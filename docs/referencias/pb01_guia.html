¿De qué va este proyecto?

Construís en equipo un sistema RAG completo end-to-end: corpus propio, índice vectorial, generación anclada al contexto, evaluación mínima, logging y visualización con Streamlit. Es la misma arquitectura que las live reviews de los Sprints 8–10, pero aquí la cerráis vosotros de punta a punta y con un dominio nuevo.

Integra lo que habéis visto de RAG Engineering: ingesta, chunking y embeddings (Sprint 8), bases vectoriales y retrieval (Sprint 9), y generación, evaluación e interfaces (Sprint 10).

Una pieza de un puzzle

Este Project Break es la primera pieza de un proyecto incremental. Diseñad el retrieve/generación como funciones claras (p. ej. rag_ask(consulta) -> str), separadas de la UI, para poder reutilizar el código después.

Objetivos generales

Desarrollar un sistema RAG modular y usable que:

  1. Integre un corpus de documentos externos.
  2. Indexe y recupere información con una base vectorial.
  3. Genere respuestas ancladas al contexto recuperado.
  4. Tenga arquitectura modular y mantenible.
  5. Incluya evaluación mínima, logging básico y visualización con Streamlit.
No hace falta inventar un producto distinto: reutilizad la estructura de las prácticas de clase y cerradlo como entregable de equipo. Elegiréis una temática y curaréis el corpus vosotros mismos.

Trabajo en equipo y Git

Gestionáis el proyecto con GitHub desde el primer día. La organización interna del equipo (quién hace qué y en qué orden) la decidís vosotros, pero las reglas mínimas son obligatorias.

Reglas mínimas

  • Crear el repositorio en GitHub al inicio del proyecto
  • Mínimo una PR revisada y mergeada por cada miembro del equipo
  • Integrar con pull requests hacia develop; resolver conflictos en la rama antes del merge
  • No subir claves — usar .env y .gitignore
  • README del repo: clonar, instalar dependencias, configurar API keys, indexar el corpus y ejecutar CLI + Streamlit

Corpus & temáticas

No hay un zip de datos cerrado en este enunciado: el corpus lo curáis vosotros. Vuestra tarea es investigar las fuentes, descargar, filtrar y documentar el corpus final. Fijad la temática cuanto antes para no consumir demasiado tiempo en la investigación.

Requisitos del corpus

  • Al menos 2 formatos distintos (p. ej. PDF + MD/TXT, o PDF + CSV)
  • Preferible combinar texto (guía/FAQ/PDF) con algo estructurado (CSV)
  • Volumen razonable (5–20 documentos, o 1 PDF grande + FAQ + CSV)
  • Documentar las fuentes en el README (enlaces y fecha de descarga)
  • Evitar PDFs solo imagen (escaneados sin texto) y web scraping agresivo
Elegid una de las cuatro temáticas. Si os surge otra que no esté en la lista, proponedla a los profesores para valorar su viabilidad. Las temáticas de clase (calidad del aire, agenda cultural) no entran: el objetivo es un corpus nuevo.

🚇 1 · Transporte / abonos

Asistente sobre tarifas, zonas, abonos y condiciones de viaje (p. ej. CRTM / Metro / Cercanías).

Fuentes: CRTM, Renfe Cercanías, Open Data Madrid / EMT, FAQ oficiales de títulos y tarifas.

Ej.: ¿Qué zonas cubre el abono mensual? ¿Puedo usar el mismo título en Metro y Cercanías?

🎓 2 · Becas / trámites

Asistente de una convocatoria o trámite concreto (requisitos, plazos, documentación).

Fuentes: sede.educacion.gob.es / becas MEC, SEPE / Seguridad Social, sedes autonómicas, un PDF acotado del BOE.

Ej.: ¿Qué requisitos pide? ¿Qué documentos entregar? ¿Hasta qué fecha se solicita?

🏞️ 3 · Parques / turismo sostenible

Asistente del visitante (normas, rutas, restricciones, temporadas).

Fuentes: miteco.gob.es (parques nacionales), webs de parques (Picos, Doñana, Guadarrama…), open data de turismo regional.

Ej.: ¿Puedo llevar perro? ¿Hay restricción de acceso en verano? ¿Qué rutas son para principiantes?

🏊 4 · Deporte municipal

Asistente de instalaciones municipales (normas, tarifas, reservas, horarios).

Fuentes: open data del ayuntamiento, PDFs de normas/tarifas deportivas, web municipal de deportes.

Ej.: ¿Cuánto cuesta el abono de piscina? ¿Puedo reservar siendo no empadronado?

Las listas completas de recursos y URLs orientativas por temática están en el enunciado original (README.md). Empezad por ahí para localizar los PDFs y CSV.

Capacidades del sistema

1 · Pipeline offline (indexación)

Documentos → limpieza → chunking → embeddings → ChromaDB persistente.

2 · Retrieval

Dada una pregunta, recuperar top-k chunks y mostrar el contexto (CLI y/o Streamlit).

3 · Generación RAG

Respuesta del LLM usando solo el contexto; si no hay evidencia, abstenerse («no sé» / «no está en los documentos»).

4 · Interfaz

Streamlit con chat, contexto visible y métricas simples (k, nº chunks, tiempo, modelo).

Pipeline completo

Documentos ↓ Ingesta + limpieza ↓ Chunking ↓ Embeddings ↓ ChromaDB (persistente) ↓ Retriever (top-k) ↓ Contexto + prompt ↓ LLM → respuesta ↓ CLI + Streamlit

✅ El sistema debe

  • Anclarse al corpus
  • Citar o mostrar fuentes/chunks
  • Admitir «no sé» si no hay evidencia en el contexto

🚫 No se permite

  • Inventar datos fuera del corpus
  • Depender solo de un notebook sin módulos
  • Mezclar indexación y UI de forma inseparable
Separad offline (preparar e indexar: --prepare / --index) de online (preguntar: --query retrieval / --ask RAG completo). Usad prompts con bloques claros: instrucciones + --- CONTEXTO --- + --- PREGUNTA ---. Al indexar, guardad al menos el metadato source.

Requisitos obligatorios

  • Corpus externo curado por el equipo (≥2 formatos)
  • Pipeline: load → clean/chunk → embed → ChromaDB persistente (con metadatos mínimos, p. ej. source)
  • Separación indexado vs pregunta
  • Retriever top-k + contexto al prompt; MAX_CHUNKS y TOP_K documentados. Si cambiáis embeddings o límites, regenerad el índice
  • Fallback: generación usando el contexto; si no hay evidencia, abstenerse. Incluid al menos 1 pregunta fuera de corpus
  • Código modular (no un notebook monolítico)
  • Streamlit: chat + visibilidad de chunks/contexto recuperado
  • Evaluación en dos capas: retrieval (≥2 valores de K) + generación (8–15 preguntas, varias in-corpus + ≥1 fuera)
  • Logging básico: pregunta, k, nº chunks, tiempo, modelo
  • Tabla simple de métricas en Streamlit
  • API interna usable sin UI: responder(pregunta) -> dict y, opcional, rag_ask(consulta) -> str

Partes del proyecto

01

Tema y corpus

Cerrar dominio y datos antes de programar el pipeline completo

  • Elegir la temática del RAG
  • Localizar y descargar fuentes; dejar el corpus en data/ (o documentar descarga reproducible)
  • Acordar el alcance: qué preguntas sí / no debe responder el asistente
  • Redactar en el README: tema (2–3 líneas), fuentes concretas, formatos (≥2), 5 preguntas de ejemplo y confirmación de datos públicos / uso educativo
02

Indexación y retrieval

Pipeline offline + búsqueda semántica usable (alineado con S8–S9)

  • Load → clean/chunk → embed → ChromaDB persistente (incluye source)
  • Separar indexado de la pregunta (--prepare / --index vs --query)
  • Documentar MAX_CHUNKS y TOP_K en config.py / README
  • Demo 1: indexar el corpus. Demo 2: --query — solo retrieval + contexto
  • Probar ≥2 valores de top-k en la misma pregunta; anotar en el informe qué cambia (ruido vs acierto)
  • Logging básico al consultar (pregunta, k, nº chunks)
Si cambiáis embeddings o MAX_CHUNKS, regenerad el índice desde cero.
03

Generación, evaluación y API interna

Cerrar el ciclo RAG y dejar el componente reutilizable

  • Prompt con bloques claros (instrucciones + contexto + pregunta) + generación con el LLM elegido
  • Fallback / abstención si no hay evidencia; probar al menos un caso fuera de corpus
  • API interna sin Streamlit: responder(pregunta) -> dict (respuesta, chunks/fuentes); opcional rag_ask(consulta) -> str
  • Set de 8–15 preguntas en queries/ (in-corpus + ≥1 fuera) + criterios evidencia / grounding / abstención
  • Evaluación de retrieval ligera: mismas preguntas con ≥2 valores de K
  • Comando CLI: --ask — respuesta RAG completa
  • Ampliar logging: tiempo, modelo, (opcional) si hubo abstención

Criterios de aceptación (Parte 3)

  • --ask in-corpus devuelve texto + fuentes/chunks
  • --ask fuera de corpus → abstención (no inventa)
  • Prompt con secciones delimitadas
  • responder (dict) y/o rag_ask (str) callable sin UI
04

Streamlit, informe y cierre

Interfaz demostrable y entrega documentada

  • Streamlit: chat + chunks/contexto visible + tabla simple de métricas
  • README del equipo completo (instalación, indexado, CLI, UI, fuentes, capturas)
  • Informe en entregables/informe_decisiones.md con: experimento de chunking (con números), observación con 2 valores de K, 1 acierto in-corpus + 1 abstención fuera de corpus, y 3 fallos + siguientes pasos
  • Comprobar que no hay secretos en el repo y que main está listo para entregar

Experimentos opcionales Opcional

No son obligatorios ni sustituyen los requisitos. Si os sobra tiempo, elegid 1–3 y documentad: qué cambiasteis → qué observasteis → qué cambiaríais en un sistema real.

Prompt / generación

  • Restrictivo vs permisivo con una pregunta fuera de corpus
  • Temperatura 0.0 vs 0.7 en la misma pregunta

Retrieval / índice

  • Barrido de K (1, 3, 5)
  • Citas explícitas del fichero fuente
  • Bajar MAX_CHUNKS y comparar
  • Chunking A/B

Robustez

  • Pregunta vacía / basura sin llamar al LLM
  • Inyección ligera contra el prompt restrictivo

UI / contrato reutilizable

  • Misma pregunta en CLI y Streamlit
  • Chat con st.chat_input / st.chat_message
  • Feedback 👍 / 👎 en st.session_state
Fuera de estos opcionales quedan fine-tuning, hybrid search, rerankers o deploy en la nube: eso pertenece a módulos posteriores.

¿Cómo se evalúa el proyecto?

Vuestro proyecto se valora en seis áreas. La mayoría son de equipo (misma valoración para todos), y una es individual (según vuestra aportación real al repositorio). El porcentaje junto a cada área indica su peso sobre la nota. Usad estos puntos como una guía de en qué fijaros para que el trabajo esté completo y bien cerrado.

Las cinco áreas base suman el 100 % de la valoración: Desarrollo Técnico (35 %), Presentación (23 %), Git (17 %), Trabajo en equipo (15 %) y Memoria (10 %). Los Extras suman aparte, hasta un +10 % adicional.

⚙️ Desarrollo Técnico · equipo 35 %

El corazón del proyecto. Se fija en:

  • Estructura y modularización: responsabilidades separadas por módulo (load/chunk/embed/index/retrieve/generate/UI), código legible y configuración centralizada en config.py.
  • Funcionalidad: indexación completa y persistente (ChromaDB con source), retrieval coherente y generación anclada al contexto de forma consistente.
  • Robustez: abstención ante evidencia insuficiente o pregunta fuera de corpus, y buen manejo de inputs inválidos o extremos (vacío, muy largo).
  • Escalabilidad: TOP_K / MAX_CHUNKS configurables, índice regenerable y diseño listo para reutilizarse en el proyecto de Agentes.
  • Usabilidad: Streamlit con chat y contexto visibles, métricas simples y CLI clara (--index, --query, --ask).
Inventar datos fuera del corpus en lugar de abstenerse es el error más grave: la abstención cuando no hay evidencia es imprescindible.
Los nombres concretos de ficheros, funciones, variables o comandos del enunciado son orientativos: se evalúa el comportamiento y la tecnología requerida (ChromaDB, Streamlit), no que sigáis la nomenclatura exacta del README. Podéis nombrar vuestros módulos y flags como prefiráis.

🎤 Presentación · equipo 23 %

  • Expresión oral: claridad, participación repartida entre el equipo y no leer literalmente las diapositivas.
  • Soporte visual: legible, cuidado y sin sobrecarga de texto.
  • Narrativa: un hilo conductor claro que enganche a la audiencia.
  • Demo en vivo: se ejecuta sin errores bloqueantes, muestra los chunks/contexto con claridad y se recupera con soltura si algo falla.

🌿 Git · equipo 17 %

  • Estructura: buena modularización de archivos y un repositorio limpio, coherente y lógico.
  • README: todos los apartados solicitados, bien redactados y fáciles de seguir.
  • Ramas y PRs: convención de ramas clara, PRs revisadas antes de mergear y main estable al final.
  • Reparto: las ramas y PRs reflejan una división de trabajo coherente en el equipo.
  • Reproducibilidad: el proyecto se instala y ejecuta desde cero (clonar, dependencias, .env) sin ayuda extra, y el indexado y la consulta funcionan siguiendo los pasos del README.

👥 Trabajo en equipo · individual 15 %

Se valora por persona, a partir del historial de Git:

  • Volumen y consistencia: aportación proporcional a tu parte del reparto y repartida en el tiempo, no todo de última hora.
  • Calidad: mensajes de commit claros y PRs de tamaño manejable, centradas en una tarea.
  • Colaboración: revisar y comentar PRs de compañeros de forma sustancial y participar en las dudas del equipo.
Si no dejas una presencia y participación objetivas y evidentes en el flujo de Git (commits propios, ramas, PRs abiertas y revisiones), esta área puede no superarse de forma individual, aunque el proyecto del equipo salga adelante.

📝 Memoria · equipo 10 %

  • Documentación: corpus, datos, decisiones y resultados clave documentados (chunking, K, proveedor), con reflexión crítica real y no relleno.
  • Orden: bien organizada, sin errores, con extensión adecuada y fácil de navegar.

✨ Extras Opcional +10 %

Suma si aportáis algo más allá de lo pedido: funcionalidad no solicitada bien integrada, o experimentación documentada más allá de la obligatoria (ver «Experimentos opcionales»).

En resumen, un proyecto sólido: funciona de punta a punta, se ancla al corpus y se abstiene cuando toca, tiene código modular y limpio, un repositorio bien organizado con PRs reales, una memoria que explica el porqué y una presentación clara con demo en vivo.
